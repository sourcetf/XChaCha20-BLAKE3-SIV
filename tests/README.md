# Test layout

| File | What it pins |
| --- | --- |
| `src/lib.rs` (`mod tests`) | known-answer vectors, the construction's structure, SIMD-vs-scalar agreement, zeroization, avalanche |
| `tests/differential_reference.rs` | the whole public API across every internal length boundary, against vectors generated by `tools/ref_impl.py` |
| `tests/vectors_differential.txt` | 49 vectors from the Python reference (key, nonce, aad, message, ciphertext, tag), each replayed byte for byte — the *lock*, as opposed to the sampling evidence elsewhere |
| `tests/vectors_differential_large.txt` | 9 sizes from 1999 B to 1 MiB as `BLAKE3(ciphertext \|\| tag)` digests — a megabyte of message is two megabytes of hex, so the full fixture stops at 2049 B and this one exists to put the sizes *around* the tag's contiguous-buffer threshold in front of the reference implementation instead of in front of themselves. The threshold is on `48 + aad + msg` (`TAG_CONCAT_MIN..=TAG_CONCAT_LIMIT`, 2048..=65536), so in message lengths it is straddled by **2000 and 65488**, not by 2048/65536 — an earlier revision of this row said "64 KiB, and 65 537", a later one said "the 4 KiB tag-buffer switch"; neither boundary exists, and 65537 is a byte-length figure from the pre-`v0.3` 80-byte head |
| `tests/security.rs` | security properties: property-based and fuzz |
| `tests/timing.rs` | the dudect-style timing screen — **release builds only** (`#![cfg(not(debug_assertions))]`) |
| `tests/variable_latency.rs` | an inventory of every literal `/` and `%` in the non-test source of `src/lib.rs` **and** `src/witness.rs` (only the literal operators) — the operations no tool here can see, so a new one fails the test until a human writes down why it is not a secret-dependent latency — plus a per-file table of the control-flow keywords (`if`/`while`/`for`/`loop`/`match`) in `src/lib.rs` and `src/witness.rs`, which fails when a count moves so each branch is re-audited by hand |
| `tests/decision.rs` | the accept/reject decision — the detector `tools/fi_check.sh` uses to show that one skipped gate accepts a forgery on the opt-out build (`--no-default-features`) and does not on the `hardened` one (which is the default); also the message-commitment property (`a_tag_from_one_message_must_not_authenticate_another`) |
| `tests/decision_scope.rs` | the *shape* of the decision, read out of `src/lib.rs`: the suppression names one function and nothing else, that function contains only the two gate branches, the second gate is an independently *shaped* comparison over volatile re-reads of the same two values, the outcome is fail-closed through two slots checked in series, and where `ultra` folds its witness agreement in. Source-shape tests, because these are the properties a valgrind entry and a fault campaign depend on and neither can check them |
| `tests/mac_commitment.rs` | the commitment property a *fault* breaks: a tag issued for one message must not authenticate another, in a form that tolerates `ultra` refusing to issue the tag at all (`tools/fi_check.sh`'s `msg-independent-mac-*` rows) |
| `tests/construction_inventory.rs` | the *completeness* of the security analysis: the number of call sites of each primitive (the seven uses `SECURITY-ANALYSIS.md` §4.10 reasons over, plus the unkeyed BLAKE3 hash that is the one cryptographic call outside the construction), and the structural separation lemmas that make the composition need no joint assumption about ChaCha20 and BLAKE3 — S1, the three keyed-BLAKE3 input spaces are disjoint by their 8-byte domain prefixes, and S2, the derivation nonce does not use XChaCha20's NUL padding (verified non-vacuous by planting an eighth call site of one of the *listed* names and by equating two of the three domains; the listed names now include `blake3::Hasher::new_keyed`, the single keyed seam, because an audit evaded the count by adding a second direct `new_keyed` use — a *different* unlisted spelling could still evade it, so the count is a tripwire rather than a proof) |
| `tests/locked.rs` | `locked` on its own (not only bundled into `ultra`): the kernel's `smaps` accounting for the mapping that *contains the key* — a per-mapping judgment, because "locked memory went up" is satisfied by locking anything (a `Some(0)` from a channel that demonstrably reports locks is a failure now; an audit made the test lock a decoy buffer and it passed) — and the **refusal path**: the allowance is exhausted through the public API to require that a refused `LockedKey::new` is reported as an error and returns every page's charge (a mutant that ignores `lock_range`'s error fails it; the audit had noted this arm was only ever *skipped*). The refusal arm **fails** rather than skipping when it cannot exhaust the allowance (a host with a very large `RLIMIT_MEMLOCK`, or one holding `CAP_IPC_LOCK`): a skip under libtest's captured stderr is indistinguishable from a real assertion, so an unexercised refusal path is a failure by default, and `XSIV_ALLOW_UNEXERCISED_REFUSAL=1` turns it back into a visible `SKIPPED (allowed by …)` for a host that genuinely cannot exercise it |
| `src/proofs.rs` | Kani harnesses (proofs, not tests), planned into CI shards by `tools/kani_shards.py` (which fails if a harness matches no shard, so a new one cannot go unproven) and type-checked without Kani by `tools/check_kani_cfg.sh`. Run them with the flags the entry points pass — `cargo kani --features pure -Z stubbing -Z unstable-options --extra-pointer-checks` — because seven of the thirteen harnesses use `#[kani::stub]` and fail at *compile* time without `-Z stubbing` (an audit ran the bare command when there were twelve: 6/12 never reached verification; with the flags, all SUCCESSFUL — the thirteenth, the concrete tag comparison, was added later and is both stubbed and verified) |
| `src/witness.rs` | the `ultra` build's independent second implementation of the whole construction — a from-scratch ChaCha20/HChaCha20/keyed-BLAKE3 the crate cross-checks bit for bit, with its own unit tests against the crate's primitives |
| `tests/threads.rs` | concurrent use: 32 threads racing the first call, then agreeing on every ciphertext and tag |
| `tools/stack_residue.sh` | (a tool, not a test) the stack scan that asks whether key material survives a round trip in the call chain — it reports rather than gates, because what it measures is residue in frames the compiler chose |

## Where the security evidence actually comes from

Several checks in the usual "audit a self-rolled AEAD" list could **not** be run
in the environment this crate was developed in. This file records what was run,
what was substituted, and what therefore rests on reasoning rather than tooling —
so a green run is not read as more than it is.

Two properties it needs are pinned by tests: `nonce_reuse_does_not_reuse_the_keystream` and `the_key_material_block_is_not_the_message_keystream`. |

A 3x window cannot be gated on, so CI runs the screen as its own non-blocking job and the strict assertion (t < 10) applies where the host is quiet — `verify.sh --deep` reports `t < 0.4`. Each test prints its own resolution because it varies with load and build: ~0.16 µs/op in a quiet release run here, a few ns/op on a GitHub release runner, and ~60 ns/op in CI's debug job. A `ct_eq` → `==` regression is tens to hundreds of ns, so a gross one is within the screen's reach on a quiet host — but the deterministic evidence is ctgrind, not this. `timing_screen_can_detect_a_real_difference` keeps the detectability floor visible: a deliberate 67 ns/op difference measures `t = 3244`. |

The script's own virtual-to-file mapping is asserted against `objdump -d` before any fault is written, because an earlier version got that offset wrong (LMA instead of file offset, 4 KiB out) and reported a believable zero. `tools/ctgrind.sh` also plants a secret-dependent branch inside `decrypt` and requires its own check to fail, which is the control for the suppression's scope. Summary: one skipped branch accepts a forgery on the opt-out build, one skipped gate or corrupted gate value does not on the `hardened` build, rewriting the computed tag is accepted by `hardened` alone and rejected by `dual-mac`/`ultra` (which also reject a fault in the arithmetic both derivations share, because the witness computes it again), and a skipped in-place wipe is caught by `tests/security.rs` |
| Fault injection | **not covered, and not claimed** | No tool in this suite models a glitch — Miri, Kani, ctgrind, TSAN and libFuzzer all assume correct execution. `tools/fi_check.sh` and `tools/fi_instruction.sh` model *single* faults, in the source and in the compiled decision, and both find accepting faults in the opt-out build; neither is a bench, and neither injects a fault *timed* against the data it must disturb. Encryption-side faults, by contrast, degrade to rejection, because the tag is computed over the plaintext. A hardened implementation would need a validated countermeasure set and a fault-injection bench — see README's "What is not defended against". |

### What these checks do not reach

Every gate above has an edge, and an edge that is written down is a limit rather than a
surprise:

- **The exhaustive byte-position scans stop at msg_len ≤ 300 and aad_len ≤ 130**
  (`tests/differential_reference.rs`'s `differential_every_position_is_authenticated`
  and `differential_every_aad_bit_is_authenticated`: the `msg_len > 300` and
  `aad_len > 130` filters. Earlier revisions of this row quoted line numbers, which
  drifted twice; the test names are the stable reference). Every position of a corrupted
  ciphertext or tag within those sizes is tried; above them the coverage is random
  sampling, and the sizes that matter most (the SIMD widths, the 2000/65488 pair that
  straddles the tag's contiguous-buffer switch, 1 MiB) are checked at *boundaries*
  rather than exhaustively. An exhaustive
  scan at 1 MiB would be 2^20 signature verifications per position class, which is why
  the fixture holds digests for the large sizes instead.
- **The differential fixture is 58 vectors** (49 full + 9 digests). It is a lock, not a
  sample: its job is to pin specific sizes against the independent reference so a
  format change cannot pass unnoticed. The *sampling* evidence is elsewhere -- the
  scheduled 4000-random-vector differential (`tools/broad_differential.py`) and the
  fuzzing, neither of which is committed as a fixture because neither is stable.
- **There is no performance gate.** The numbers in `performance.md` are measured on a named
  host, with the method stated; a threshold that runs on a shared runner would gate
  CPU noise, and the same measurement that rules out a timing gate (t ≈ 11 with no
  possible cause) rules out this one. The method is scripted rather than prose —
  `tools/bench_3pass.sh` runs the three configurations × three passes with the rotated
  order, and `tools/bench_summarise.py` prints the tables — so a refresh is a command,
  not a retyping exercise. What *is* enforced is the correctness side: the
  accelerated paths are held byte-identical to the scalar one, so a "faster" change
  that alters output fails the KATs, the differential fixtures and
  `test_all_accelerated_paths_agree_on_a_boundary_corpus`.
- **The statistical timing screens cannot gate on a shared runner** (see the
  `timing-instrument` row), and **the deterministic constant-time gate is ctgrind**,
  which by construction cannot see a leak with no branch and no index -- that class is
  `tools/cache_profile.sh`'s, whose counts mode is deterministic and whose trace mode
  needs a valgrind that can start `lackey`.
- **Memory, not just length.** `decrypt` holds twice the message (the caller's
  ciphertext plus the plaintext it allocates) and `encrypt` holds two copies as well;
  both are fallible, but the peak is a property of the *call*, so `decrypt_bounded` is
  what a service should use and a cgroup limit is what a deployment should set.
- **A measurement tool can lie in ways its output does not show.** `tools/fi_instruction.sh`
  spent several revisions computing its virtual-to-file mapping from `objdump -h`'s LMA
  column instead of its file offset (`Size VMA LMA File off` — the regex took three numbers
  and used the third), which is a 4 KiB shift on these binaries: every fault landed outside
  the function, and the tool printed a believable map with zero acceptances. The fix is not
  only the correct column but an *assertion* — before a single fault is written, the bytes at
  the computed file offset must be the instruction `objdump -d` shows at that address. The
  same rule applies to any new tool here: a mapping, a filter or a symbol lookup that can be
  wrong without changing the shape of the output needs a check against a second source of
  truth, not just a plausible-looking result.
- **Collision bounds are derivations, not tests, and the tests around them check the
  premises.** `SECURITY-ANALYSIS.md` §4.5 derives the tag-collision level (`2^128`, the
  birthday bound of the 256-bit chaining value the whole 65-byte tag is a function of) and
  §3's Corollary derives what a collision would leak (`C₁ ⊕ C₂ = M₁ ⊕ M₂` under one nonce,
  not merely an equal tag). No harness can falsify either: a collision search is a
  computation, and the event is out of reach by design. What *is* pinned is the premise of
  the derivation — that the tag is exactly the root XOF of the encoded input, with no step
  that could add entropy — by `test_tag_matches_blake3_over_the_documented_input`, the
  published keyed-BLAKE3 KATs and the `ultra` witness's independent recomputation. §5's rows
  9 and 16 say the same thing from the falsification side.
- **`VmFlags` is only faithful on a native host.** `unlocking_restores_core_dump_inclusion`
  (`tests/locked.rs`) is the only check of `ultra`'s `locked` layer that reads the *kernel's*
  view — `dd` in `/proc/self/smaps` for the mapping holding the buffer — and that view does not
  exist under an emulator: measured on this host, `qemu-aarch64` runs a successful `mlock` and
  `madvise` with `VmFlags` staying `rd wr mr mw`, because the emulator keeps guest mappings in
  its own bookkeeping and does not synthesize this field. The test therefore skips (loudly,
  naming this) when the mapping it reads does not even show the `lo` the sibling
  `the_key_itself_is_locked` has already observed, and the *call* is pinned instead by
  `the_dump_advice_is_issued_on_the_right_range`, which asserts against the shipped source that
  `MADV_DONTDUMP`/`MADV_DODUMP` are 16/17, that both are passed to a *three*-argument `madvise`,
  and that both ranges are page-aligned. Verified non-vacuous by three planted defects: reverting
  the unlock call to `MADV_DONTDUMP` (caught by both tests), and changing the constant to 4 (caught
  by the source check). The effect on native aarch64 hardware is *not* covered anywhere here.
- **The coverage floor is global, not per-path.** 95% over everything measured here
  cannot be satisfied by editing exclusions, but it also cannot tell *which* path was
  lost -- it fails, and the answer is in the lcov artifact and the diff.

### Tooling notes

- **valgrind without root.** `sudo` needs a password here, but `apt-get download`
  does not, and valgrind's binaries run from an extracted package:
  `tools/ctgrind.sh --setup`.
- **The ctgrind binary must be static.** Dynamic linking needs valgrind to
  redirect `strcmp` in `ld-linux`, which needs libc debuginfo in a path valgrind
  can only search as root. Building with `-C target-feature=+crt-static` removes
  the dynamic linker and the problem with it. `strip=none` is required too, or
  every frame prints as `???` and the suppressions cannot match.
- **The RustSec database.** `git clone` from github.com fails on this network.
  Fetch the tarball through the GitHub API instead, and note that both
  `cargo-audit --db` and `cargo-deny` need it to look like a real git repo (an
  `origin` remote), so `cargo-deny` expects it at
  `<db-path>/advisory-db-<hash-of-url>`.

- **What ctgrind does not cover.** Two things, worth stating rather than implying.
  Code the tests never execute: the check reports only what runs, which is why
  `tests/ctgrind.rs` drives the decision in *both* directions with poisoned inputs
  now instead of only the rejection. The public `ConstantTimeEq` impls that return a
  `bool` stay outside it for a related reason — their final conversion branches on
  the comparison by construction, because a `bool` is what the API returns, and no
  entry is allowed to suppress them. And branches the optimizer turns into `setcc`
  or `cmov`: memcheck does not report those at all (measured — see
  `secret_dependent_branch` in `tests/ctgrind.rs`, which is shaped the way it is
  because of that). The second class is what `tools/cache_profile.sh` and the
  statistical screen exist for.

- **`mutants.out/` is the record of the run that produced it; what is enforced is the
  mutant→outcome mapping, not the coordinates.** The directory is cargo-mutants 27.1.0's
  output for the run of 2026-10-02T20:24Z (17 mutants, 15 caught, 2 unviable, 0 missed;
  the command in the CI mutation step, run from the repository root, which writes this
  directory in place), added in `a2a046d`. Every recorded line/column number, the diff
  hunk headers in `mutants.out/diff/`, and the line numbers in `caught.txt` and
  `unviable.txt` are the coordinates of the revision the run was made against (that
  `a2a046d` tree, whose `accept_or_reject` starts at line 2428). They are **not** kept in
  step with HEAD: at `ca5b8a8` that function starts at 2659 (+231) and at `e340df2` at 2690
  (+262), and it has moved further since, so a reader who follows a recorded line number
  lands in the wrong place. It is still worth refreshing
  by re-running the campaign, which is what re-syncs the coordinates — and refreshing is
  also how the `decrypt_bounded` bound mutants were found to be uncaught (the run named a
  test set that did not witness the new code), so treat "the diffs look old" as a
  finding, not as cosmetic. `cargo mutants` also renames the *previous* run to
  `mutants.out.old/`, which is ignored rather than committed: it is stale by
  construction. (It was tracked until this was noticed, which is ~1 MB of diffs against
  line numbers from an older revision in every mutation run's commit.)
  **The enforced invariant is the mutant set and its outcomes**, keyed on (function,
  genre, replacement, occurrence within that function): the CI mutation job keeps the
  committed directory aside, runs the campaign, and compares the two with
  `tools/mutation_evidence.py`, which deliberately ignores the fields that move every run
  (line numbers, durations, log paths) — a gate that failed on those would fail on every
  unrelated edit and be deleted within a week. So "the evidence describes this source"
  holds at the mapping layer only: a mutant in the committed evidence that no longer
  exists in the source fails the gate, and so does one whose outcome changed, but a
  directory whose coordinates have already drifted passes as long as the mapping matches.
  A failure means the file to commit is the refreshed `mutants.out/`, and the tool prints
  the command.

- **Valgrind suppressions match functions, not source lines.** That is the whole
  reason `tests/ctgrind.supp` may only name `accept_or_reject`. An entry permits
  every conditional jump in the function it names, so one naming `decrypt` reads as
  "the decision is permitted" and behaves as "any branch anyone later adds to
  `decrypt` is permitted". One did exactly that, and a planted leak inside
  `decrypt` passed the check — measured as 6 reports with no suppression file and 0
  with it. The file now holds one entry, `tools/ctgrind.sh` refuses to run if an
  entry names anything else, and the script's self-test plants that leak and
  requires a failure. Startup noise is not suppressed at all: reports are
  *classified* by whose frame they touch, which does not depend on valgrind's or
  Rust's version (see the header of `tests/ctgrind.supp` for the history).

```sh
# advisories, both tools
curl -sL https://api.github.com/repos/RustSec/advisory-db/tarball | tar xz
cd rustsec-advisory-db-* && git init -q && git add -A && git commit -qm db \
  && git remote add origin "$PWD"
cargo audit --db "$PWD"
# cargo-deny wants it under the name it derives from the URL:
mkdir -p /tmp/adb/dbs && cp -r "$PWD" /tmp/adb/dbs/advisory-db-3157b0e258782691
cargo deny --offline check
```

## Notes on specific tests

- **`kat_regression_lock`** duplicates the in-crate KATs with values from
  `tools/ref_impl.py`, so a change that silently alters the wire format fails
  even if someone "fixes" the in-crate expectation to match. It is a *lock* — a copy
  from the same generator, catching an edited expectation — and not a second
  implementation: its independence is bounded by that, and the independent witness is
  the differential fixture, which is produced by `tools/ref_impl.py` and replayed
  against it. It caught a real mistake during development (the first version was
  hand-typed from an older construction), which is exactly its purpose.
- **`prop_ciphertext_bit_flip_rejected`** and its tag/AAD siblings are sampled — each case
  draws one bit position — which is the property a truncated
  or prefix-comparing MAC would violate. The exhaustive per-position sweeps live in
  `tests/decision.rs` and `tests/differential_reference.rs`.
- **`prop_nonce_reuse_behavior`** pins what SIV promises under nonce reuse:
  identical inputs give identical output, different inputs give different tags,
  and both still authenticate. Reuse costs confidentiality, not
  authenticity.
- **`test_all_accelerated_paths_agree_on_a_boundary_corpus`** folds every
  ciphertext and tag byte of a corpus that crosses every internal boundary into
  one digest, and compares it with a constant. That constant was produced
  identically by every backend with a committed runner: x86_64 with AVX2
  (native), aarch64 under `qemu-aarch64` (NEON), i686 under `qemu-i386` (no SIMD
  backend at all, pure scalar), riscv64 under `qemu-riscv64` (scalar-only, 64-bit
  RISC-V), powerpc64 under `qemu-ppc64` (big-endian, scalar) and s390x big-endian
  interpreted by Miri, so it is
  a cross-implementation equivalence check rather than a known-answer test. The
  cross-execution CI job runs it on the aarch64, i686, powerpc64 and riscv64 targets, and the Deep
  Miri job (and `verify.sh --miri`) runs the s390x cross-interpretation. A
  no-AVX2 x86_64 host (SSE2 only) was part of the original measurement but has
  no committed runner, so it is not counted as an entry point; the SSE2 loop is
  held to the scalar reference by `test_x86_simd_kernels_match_scalar` wherever
  the host can execute it. (This row used to name
  `qemu-x86_64 -cpu Nehalem` as the SSE2 runner; no script or CI job in this
  repository runs it.)
- **Miri covers every accelerated path**, not just the default one: the AVX2
  kernel runs when the build enables the feature (`detect_avx2` reports the
  compiled feature set under Miri, since it cannot run CPUID there), and the NEON
  kernel by cross-interpreting aarch64. ASan is not available for the aarch64
  target here (it cannot link a static musl libc), so for that backend the
  evidence is Miri plus byte-equality with the scalar reference.
- Timing tests are `--release` only, and not by convention: `tests/timing.rs` carries
  `#![cfg(not(debug_assertions))]`, so a debug build runs no timing test at all. Run
  them with `cargo test --release --test timing`. (This row said `--test security`,
  which runs the security suite and *no* timing test — `tests/security.rs` says in its
  own header that the timing screen lives elsewhere.)

## Running the extra checks

```sh
cargo test --release                        # unit + differential
cargo test --release --test security        # property + deterministic fuzz (timing is its own target)
./verify.sh                                 # fmt, clippy, docs, tests, cross-build
./verify.sh --deep                          # ...plus Kani, aarch64 under qemu, Miri,
                                            #   ctgrind, cargo-deny, fuzzing
./verify.sh --ctgrind                       # just the constant-time check (with its control)
tools/mutation_check.sh                   # plant known bugs; the checks must catch them
cargo bench --bench compare               # head-to-head vs RustCrypto's chacha20poly1305
./verify.sh --deny                          # just cargo-deny
FUZZ_SECONDS=600 ./verify.sh --fuzz         # a longer fuzz soak
cargo +nightly miri test --release --features pure --lib    # UB detection (slow: ~20 min
                                                            # for the whole lib suite; the
                                                            # `pure` is belt-and-braces on
                                                            # x86_64 -- Miri's CPU-feature
                                                            # detection reports nothing, so
                                                            # the C kernels are never
                                                            # dispatched with or without it)
```
